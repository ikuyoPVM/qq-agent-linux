# 双机接力 handoff · 使用手册

一个插件，两台机器：**服务端**（目前的 VPS）和**本地电脑**共用同一个 bot。本地接管前，服务端自动下线并把"大脑"同步过来；本地交还时，等记忆落盘后回传，服务端自动上线。

> 实现方式：不碰核心代码，只新增 `plugins/handoff/`。所有跨机请求都由**本地**发起；服务端只开一个被动监听口。

---

## 1. 先认清一个物理约束

**同一个 QQ 号不能同时在两台机器在线。** 所以：

| 模式 | 交接时要做什么 | 离线时长 | 需要人工登录吗 |
|---|---|---|---|
| `single`（同号，默认） | 停对端 QQ → 本端拉起 QQ | 30 秒 ~ 2 分钟 | 通常要（扫码或点"登录"） |
| `dual`（两个号） | 只暂停对端，QQ 不动 | 几秒 | 不需要 |

**服务端必须打开 QQ 自动登录**：交还后服务端要自己把 QQ 拉起来并登录；没开的话，服务端上线那一步就要人工去点「登录」。

如果本机 QQ 勾了"自动登录"，`single` 也能做到全自动；否则每次交接要人工点一下。**插件不迁移 QQ 登录态**（跨机复制登录数据有风控风险，也不平台合规）。

## 2. 角色与拓扑

```
本地电脑 (role=client)                    服务端 (role=server)
  浏览器控制台 127.0.0.1:18191         插件监听 0.0.0.0:18190
        │  ── POST /handoff/takeover ──────────▶ 暂停 → 下线 → 打包
        │  ◀── 快照信息（加密）─────────────────
        │  ── POST /handoff/snapshot/<id> ─────▶ 回密文包（二进制）
        │  落盘 → 重启 → 拉起 QQ/SnowLuma
        │  ── POST /handoff/ack ───────────────▶ 保持离线
        │
        │  ── POST /handoff/return（密文包）────▶ 落盘 → 重启 → 上线
        │  ◀── 结果（加密）────────────────────
```

服务端端口**不对公网时也能跑**（比如两端在同一 VPN/Tailscale 网段），把 `listenHost` 改成内网地址即可。

## 3. 准备密钥（在任意一台机器上执行一次）

```bash
# 1) 共享密钥（两端填同一串）
openssl rand -base64 48

# 2) RSA 密钥对（本地电脑持有私钥，服务端只填公钥）
openssl genrsa -out client_priv.pem 2048
openssl rsa -in client_priv.pem -pubout -out client_pub.pem
```

- `client_priv.pem` → 本地电脑 → 「RSA 私钥」
- `client_pub.pem` → 服务端 → 「RSA 公钥」

> **设置框只支持单行**：粘贴多行 PEM 时换行会被压掉，插件已经能识别三种形态：
> `-----BEGIN X----- MIIB… -----END X-----`（换行变空格）、`-----BEGIN X-----MIIB…-----END X-----`（换行直接没了）、
> 以及只粘 base64 正文（自动补壳）。如果字段有长度上限把密钥截断了，状态页会明确写「内容只有 N 个 base64 字符，多半被输入框截断」。

> 粘贴时请**整段**复制（含 `-----BEGIN …-----` 和 `-----END …-----` 两行）。
> 插件对常见粘贴事故做了容错：只粘 base64 正文、换行被压成一行、被引号包住、换行变成字面量 `\n` 都能自动纠正；
> 但「只粘了一半」和「公钥/私钥填反」这类内容错误无法猜出来，会在状态页和日志里给出明确提示。

加密方式（写清楚免得误会）：**正文永远走 AES-256-GCM**（密钥由共享密钥 HKDF 派生）；RSA-2048 用来 ① 本地请求的 RSA-PSS 签名（证明身份）② 回程用 RSA-OAEP 包一层会话密钥。RSA 一次只能加密约 190 字节，**不可能**直接加密几十 MB 的同步包。

## 4. 配置

打开「插件」页 → 双机接力 → 设置。

### 服务端（`role=server`）

| 键 | 填什么 |
|---|---|
| 角色 | `服务端` |
| 共享密钥 | 第 3 步那串 |
| RSA 公钥 | `client_pub.pem` 全文 |
| 监听地址/端口 | `0.0.0.0` / `18190`（防火墙放行 TCP 18190） |
| IP 白名单 | 强烈建议填家里宽带的公网出口 IP |
| 插件黑名单 | 不想同步给本地的插件 id（本插件 `handoff` 永远排除） |
| 技能黑名单 | 同上 |

### 本地（`role=client`）

| 键 | 填什么 |
|---|---|
| 角色 | `本地电脑` |
| 共享密钥 | 与服务端完全一致 |
| RSA 私钥 | `client_priv.pem` 全文 |
| 服务端地址/端口 | 服务端公网 IP / `18190` |
| 插件黑名单 | 不想回传给服务端的插件 id |
| 技能黑名单 | 同上 |

> 两端的黑名单**各管各的方向**：服务端的黑名单决定"发给本地时排除什么"，本地的黑名单决定"回传时排除什么"。`handoff` 自己两端都不同步（它的密钥当然不会跟着走）。

---

### 网络前置检查（很容易在这里卡住）

1. 服务端插件监听 `0.0.0.0:<listenPort>`，并且**系统防火墙要放行**这个 TCP 端口（Windows：入站规则）。
2. 看服务端网卡地址：
   - 是 `192.168.x.x / 10.x.x.x` → 它在路由器 NAT 后面：
     - 本地和它**在同一局域网** → `peerHost` 填它的**内网地址**（最简单）；
     - **不在同一网络** → 在路由器上做端口转发（TCP 18190 → 那台机器的内网地址），`peerHost` 填公网 IP；家宽公网 IP 会变，建议配 DDNS；
     - 运营商给的是**大内网**（没有真正公网 IP）→ 端口转发无效，改用 Tailscale / ZeroTier 这类组网，`peerHost` 填虚拟网 IP（插件监听 0.0.0.0，支持）。
3. 本地控制台点 **「测试服务端连通性」**：
   - `✅ 端口通` → 再点接管；
   - `ECONNREFUSED` → 端口没人监听：服务端插件没启用、端口填错，或路由器没做转发；
   - `ETIMEDOUT` → 被防火墙/NAT/云安全组丢包；
   - `ENOTFOUND` → `peerHost` 写错或 DNS 有问题。

## 5. 日常使用

本地端启用插件后，用浏览器打开 **<http://127.0.0.1:18191/>**（建议存成书签）。页面上三个按钮：

- **接管到本地**：让服务端下线并把数据同步过来，然后重启本地上线（期间服务端 QQ 会退出，本地 QQ 可能需要登录）；
- **交还服务器**：本地先暂停、等记忆落盘、停 QQ，再把数据回传，服务端自动上线；
- **刷新状态**：角色、状态、上次同步方向与时间、最近错误。

页面每 5 秒自动刷新一次，交接进行中会显示已用秒数。不想开页面也可以直接命令：

```bash
curl -X POST http://127.0.0.1:18191/local/takeover   # 接管
curl -X POST http://127.0.0.1:18191/local/return     # 交还
curl http://127.0.0.1:18191/local/status             # 状态
```

> 服务端（role=server）也会在本机开一个**只读**控制台（同样 127.0.0.1:18191）：能看角色/监听状态/密钥自检，
> 但「接管/交还」按钮会禁用并提示由本地端发起 —— 服务端不自已切换自己。

> 这个页面是插件自己起的 HTTP 服务，只监听 `127.0.0.1`；关掉浏览器不影响 bot。
> 之所以不做 .bat：插件市场禁止上传 `exe/dll/bat/cmd/ps1/vbs/sh`（`BANNED_EXT`），网页是绕开这条限制、又不落地任何可执行文件的办法。

也可以在插件设置里打开「本地启动即接管」，让本地一开机就自动接管。

**串行建议**：不要两端同时打开 QQ。本地接管成功后，服务端的 QQ 是关着的；本地交还后，本地 QQ 是关着的。

## 5.5 上线时自动注入 SnowLuma

接管/交还完成后，插件上线时会自动处理 SnowLuma 注入，不用再去控制台点：

1. 拉起 QQ 前，先把 `snowluma/config/runtime.json` 的 `hookAutoLoad` 改成 `true`（SnowLuma 发现 QQ 进程就自动注入）；
2. 拉起 QQ → 拉起 SnowLuma → 等 OneBot 连上（最多 60 秒）；
3. 还是没连上，且填了「SnowLuma WebUI 密码」→ 登录 `127.0.0.1:5099`，找到**未注入**的 QQ 进程，调 `POST /api/processes/<pid>/load` 补一次，再等连接。

| 设置 | 说明 |
|---|---|
| 自动注入 SnowLuma | 默认开。关掉就回到手动点注入。 |
| SnowLuma WebUI 密码 | 可选但建议填（就是登录 5099 的密码）。只用于后备注入，不会同步给对端。 |

> `hookAutoLoad` 有可能在 SnowLuma 退出时被它自己重置回 `false`，所以插件**每次上线前都会重写一次**（幂等，已经是 true 就不动文件）。

### 只注入指定的 QQ 号（白名单 / 黑名单）

| 设置 | 说明 |
|---|---|
| 只注入这些 QQ 号（白名单） | 逗号/空格分隔，例如 `123456789, 987654321`。留空 = 不限制 |
| 不要注入这些 QQ 号（黑名单） | 同上。**优先级高于白名单** |

规则：

- 只要填了任一名单，插件就会把 SnowLuma 的 `hookAutoLoad` **关掉**（否则它会注入所有发现的 QQ 进程），改成登录 WebUI 后按号调 `POST /api/processes/:pid/load`；
- 未登录的 QQ 进程没有 uin，插件会先用 `GET /api/processes/:pid/probe-login` 探测出 QQ 号再判断；
- 因此这需要「SnowLuma WebUI 密码」可用；密码错会**立即停止重试**并记日志，避免触发 SnowLuma 的登录锁定（连续输错会锁 IP）。
- 名单留空 + 有密码时仍是"全部注入"；名单留空 + 没密码时只靠 `hookAutoLoad`。

## 6. 同步了什么

| 内容 | 说明 |
|---|---|
| `data/messages/` | 群/私聊消息存档 |
| `data/sessions/` | 会话留档（可在设置里关掉以减小体积） |
| `data/memory/`、`memory-v2/`、`cross-turn/`、`semantic-cards/` | 长期记忆 |
| `data/stickers.json`、`sticker-images/`、`whale-memes/`、`sticker-memory/` | 表情与表情包 |
| `data/her-life.json`、`self-surf.json`、`silence-ping.json`、`hot-trends.json`、`inner-life/`、`msg-reaction/`、`skills/` | 各插件状态 |
| `plugins/<id>/`、`skills/<id>/` | 插件与技能（扣掉两端黑名单与本插件） |
| `data/config.json` | **业务配置**（人设、白名单、聊天策略…） |

**不同步**：`logs/`、`electron-user-data/`、`handoff/`、`voice-hub/out/`、锁文件、各种缓存与统计。

**配置合并**：默认保留**接收方**的机器本地键 —— `server`、`snowluma`、`skills.handoff`、`skills.voice-hub`（里面有绝对路径）、`api`（模型 Key，除非你打开「同步模型 API 配置」）。要再追加，用「额外保留给本机的配置键」写点号路径。

## 7. 落盘为什么要重启

`store` 和 `memory` 都是**内存缓存 + 原子写盘**：直接改磁盘文件，运行中的进程是看不到的，还可能用旧缓存把文件覆盖回去。所以插件落盘后会：

1. 拉起 Electron 的 `app.relaunch()` 重启自己；
2. 新进程启动时读 `data/handoff/state.json`，看到 `pending=online` 就自动把 QQ/SnowLuma 拉起来并解除暂停。

如果自动重启失败（比如不是用 Electron 跑的），状态会变成 `needs-restart`，数据已经落盘，手动重启一次 QQ Agent 即可 —— 这时**不会**自动上线，避免旧缓存覆盖刚同步的数据。

## 8. 安全设计

| 项 | 做法 |
|---|---|
| 认证 | 请求头 `x-handoff-key` 必须等于共享密钥（常量时间比较） |
| 加密 | AES-256-GCM，AAD 绑定 方法+路径+时间戳+nonce |
| 身份 | 本地请求带 RSA-PSS 签名，服务端用配置的公钥验签 |
| 回程 | RSA-OAEP 包会话密钥（没有私钥解不开） |
| 防重放 | nonce 10 分钟去重 + 时间戳 ±300 秒 |
| 限流 | 每 IP 20 次/分钟；超过 429 |
| 白名单 | 可只允许固定出口 IP |
| 落盘安全 | 路径白名单（只允许 data/ plugins/ skills/、拒绝 `..`）、逐文件 sha256、先备份再写、失败可回滚 |
| 密钥保管 | 私钥只存在本地；`data/config.json` 里的密钥是掩码字段，不会随同步包发出去 |

> 仍然建议：服务端端口只对白名单开放；如果条件允许，挂一层 HTTPS 反向代理更好（应用层已经加密，TLS 是加分项）。

## 8.5 超时怎么调

慢网络（家宽上行小、跨境、手机热点）下，几个环节都要给足时间。默认值：

| 设置 | 默认 | 管什么 |
|---|---|---|
| 连通性探测超时 | 10 秒 | 「测试服务端连通性」的 TCP 握手；临时想改可加 `?timeout=20` |
| 接管/交还请求 | 300 秒 | 服务端要先暂停、等排空、停 QQ、打包，慢在这一步 |
| 大包传输 | 1800 秒 | 快照下载 / 数据回传（几十 MB 在慢速上行上可能要几分钟） |
| 上线等 OneBot | 300 秒 | 拉起 QQ/SnowLuma 后等连接 + 注入 |
| 等客户端 ack | 10 分钟 | 服务端看门狗：超时没收到确认就自动恢复上线 |
| 服务就绪 | 240 秒 | 首次拉起 GPT-SoVITS 这类重服务 |

> 这些都在插件设置里能改；改完不用重启，保存即生效（下一次请求用新值）。

## 9. 排障

| 现象 | 看这里 |
|---|---|
| `密钥不正确` | 两端 `secret` 不一致（注意首尾空格） |
| `RSA 签名校验失败` | 服务端公钥不是本地私钥对应的那把；或私钥填错 |
| `DECODER routines::unsupported` / `NO_START_LINE` | **不是路径问题**：粘贴密钥时丢了 `-----BEGIN/END-----` 头尾，或换行被输入框压成了空格。新版会自动补壳/重新折行；还是报错就看控制台状态页的「RSA 私钥」一栏（会写清是公钥填反、加密私钥还是被截断） |
| `时间戳超出允许窗口` | 两台机器系统时间差 > 5 分钟，开时间同步 |
| `连接超时` | 服务端防火墙/安全组没放行端口；或 `peerHost` 填错 |
| 接管后服务端又自己上线了 | 本地没成功发 `ack`，10 分钟看门狗触发；看服务端日志 |
| 本地状态 `needs-restart` | 自动重启没成功，手动重启本地 QQ Agent |
| 同步后语音不能用了 | `skills.voice-hub` 默认保留本机配置；如果你手动改过 `configKeepLocal`，把 `skills.voice-hub` 加回去 |
| 包太大 | 调大 `bundleMaxMB`，或关「同步会话留档」/把表情包插件加黑名单 |

## 10. 自测

```bash
# 单元测试：加密往返/篡改、签名/重放/时钟窗口、信封拆分、打包→校验→落盘→回滚、配置合并、路径穿越、黑名单
node plugins/handoff/test/handoff-test.mjs

# 端到端：起两个独立进程（server + client）、两套临时目录、两个假的"本机控制口"，
# 真实走一遍「接管」和「交还」，不会碰你现在的 bot 数据和 QQ
node plugins/handoff/test/e2e.mjs
```

e2e 断言覆盖：服务端暂停/停 QQ、客户端拿到消息/记忆/插件/技能、镜像删除、handoff 自身不同步、本机配置键保留、业务配置同步、交还后数据回写服务端。

> 测试用环境变量 `QQ_AGENT_HANDOFF_ROOT` 把插件的工作根目录指到临时目录（生产环境不要设置它）。
